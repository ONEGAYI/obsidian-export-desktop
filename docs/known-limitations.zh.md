# 已知限制与设计取舍

本页收录经审查登记、决定**维持现状**的已知限制与设计取舍，逐条说明现象、根因、为何不修与绕过方法。26.9.0 发布后的开发期已关闭七项登记（工具预扫描 comments 感知、`.render-*` 残留清扫与同文件嵌入全文回退、测试 release 门、引用正则兜底、有序列表接续编号、cmd 脚本 `%` 路径自动警告，随 26.9.1 发布）不在本页，见 [CHANGELOG](CHANGELOG.md)。

> 取舍的总原则：Obsidian 自身各视图（编辑器、阅读视图、Publish）对同一语法的渲染本就不一致，本工具在无规范可对齐处取**自洽保守**语义，并保证导出产物语义无损、可离线自包含。

## 注释转换与 Obsidian 渲染的刻意差异

`--comments convert` 把 `%%…%%` 注释转为 HTML 注释、`strip` 删除。四个子项（见下方四小节）中，「打断重启」的编号接续已在 26.9.0 发布后的开发期修复（见 [#30](https://github.com/ONEGAYI/obsidian-export-desktop/pull/30)，随 26.9.1 发布：convert 模式重启段携带接续起始编号，嵌套列表与同一列表多次被打断同样正确；strip 模式产物列表保持连续、重新解析按位置递增），其余三个子项维持现状。

### 嵌套 `%%` 按非贪心配对

- **现象**：`%% a %% b %%` 中第一对 `%%` 配对成注释、`b` 保留为正文；Obsidian 阅读视图对这类输入的渲染本身是错乱的。
- **根因**：注释标记按就近（非贪心）配对，区间内不二次解析。
- **为何不修**：Obsidian 各视图行为互不一致，没有可对齐的目标；就近配对是唯一无歧义的自洽语义。
- **绕过**：避免嵌套注释，拆写为多个独立注释。

### 注释内嵌的代码块被折叠进注释

- **现象**：注释区间里的 fence 代码块整体成为注释内容（convert 后在 HTML 注释内可见）；Obsidian 阅读视图会显示代码块内容、仅隐藏 `%%` 标记。
- **根因**：注释区间按事件流合成文本，不解析内部的 Markdown 结构——一旦解析，嵌套 `%%` 与 fence 的歧义无法收敛。
- **绕过**：需要保留展示的代码块不要包进注释。

### 注释内容合成的容器字面是近似

- **现象**：convert 产物中，注释内的列表 bullet 恒为 `-`（原文可能是 `*`）、代码块 fence 恒为三反引号（原文可能更长）。
- **影响面**：仅注释体内部的文本形态，语义无损，正常阅读不可见。
- **为何不修**：注释体是事件流合成的近似字面，保留原始字面需要回溯原文切片，收益仅限「打开 HTML 源码读注释」的场景。

### 跨块级边界的注释断开容器后重启

- **现象**：跨段落/列表项边界的注释会把列表、引用块等容器在注释处断开，注释后重启容器继续。
- **根因**：CommonMark 的 HTML 块（`<!-- -->`）无法内嵌在列表项或引用块的中间——结构性必然，不是实现缺陷。
- **已修复的部分**：被打断的有序列表在重启处的编号接续（#30）。
- **绕过**：无（结构性约束）；嵌套缩进与引用前缀会由重启容器正确恢复。
- **已知近似**：注释吞掉整个列表项时，被吞项不占编号（其 `Start(Item)` 随注释一并移除），重启段从「已发出的项数」接续——产物自身编号连续，但与 Obsidian 阅读视图（空项壳仍占号）相差被吞的项数；取产物自洽的保守语义。
- **已知近似**：重启段的字面序号恒为该段起始值（如 `2. tail` 后是 `2. third` 而非 `3. third`）——序列化器对 `List(Some(n))` 的每个 item 都写 `n.`（未打断的 start=1 列表同貌、从未显形）；按 CommonMark 重解析为 `start=2` 的有序列表，渲染编号正确递增。

源码定位：`src/comments.rs`（`rewrite_events` 主循环、`emit_comment` 的容器骨架关闭/重开与 `reopen_skeleton` 编号换算）。

## linkcheck 报告注释内的 wikilink

- **现象**：`--check` 会把 `%% [[some-note]] %%` 中的链接照常计入检查（可能报缺失），行为与 `--comments` 选项无关。
- **根因**：check 走**原文层**——直接解析源文件收集引用（`parse_raw_note_with_refs`），不做注释改写；注释改写只发生在导出渲染管线。
- **为何不修**：check 的既有语义是「看原文」——注释里的链接同样是 vault 的真实引用（你可能暂时注释掉一段但保留其链接意图）；Obsidian Publish 的 graph 同样收集注释内链接，对齐生态惯例。
- **绕过**：删除注释内的链接，或接受报告中出现这类条目。

源码定位：`src/linkcheck.rs`（`check_obsidian_ref` 及其原文层解析）。

## 渲染超时的进程树击杀平台不对称

- **现象**：外部渲染工具超时被杀时，Windows 通过 `taskkill /T /F` 连孙进程一并根治；Unix 只终止直接子进程，若卡死的孙进程（如渲染器拉起的浏览器）持有输出管道，靠 5 秒 reader 宽限兜底。
- **根因**：Unix 侧**刻意**不设进程组——`setsid` 会让渲染进程树不再随终端 Ctrl+C 终止而变成孤儿进程，对 GUI 的取消路径也没有改善，净收益为负。而 `child.kill()` 只能杀直接子进程，Windows 的 `.cmd` shim 会再包一层，所以 Windows 用进程树击杀。
- **代价**：Unix 侧孙进程持管道时 reader 线程泄漏——但 `run_command` 一定在宽限期内返回（导出不挂起）；泄漏随孙进程死亡终结、随边车进程退出回收，无跨导出累积。
- **绕过**：无需绕过（等待有界）；极端情况下手动清理残留进程。
- **参数**：单次工具调用超时 60 秒（`TOOL_TIMEOUT`），reader 宽限 5 秒（`READER_GRACE`）。

源码定位：`src/diagrams.rs`（`run_command`、`kill_process_tree`）。

## 嵌入展开的图表副本是独立资产

- **现象**：笔记 A 嵌入笔记 B 的图表段时，A 的产物自带一份渲染资产（`<宿主stem>-<hash>.svg`），与 B 自己的那份字节相同、各自存在。
- **设计意图**：**每份产物自包含**——单独取走 A 的产物树时图表链接依然有效，不依赖 B 的 assets 目录。
- **代价**：`diagram-render` 事件的 `index` 可能超过 `total`（`total` 是预扫描对**源文件自身**可渲染块的估计值，事件流契约已声明其为估计值）。
- **为何不修**：自包含是导出产物的核心承诺；嵌入密集导致渲染耗时显著时，优化方向是「运行内去重备忘录」（省去重复的工具调用，不改变产物形态）。

源码定位：`src/lib.rs`（嵌入展开）、`src/diagrams.rs`（资产命名与内容寻址缓存）。

## 同文件与跨文件 EmbedFull 的不对称

- **现象**：`MissingSectionStrategy::EmbedFull` 下，跨文件嵌入找不到目标 section 时保留**整个目标文件**；同文件嵌入经全文回退仍找不到时保留**当前切片**。枚举文档只写了 "Embed the entire note"。
- **根因**：26.9.0 发布后的开发期（#27）给同文件嵌入补了全文回退（消除「嵌入片段内的 `![[#Other]]` 只在切片内查找」的局部性），但回退后仍找不到时的兜底保留物沿用了切片；跨文件路径的兜底自古是整文件。差异仅在「经由跨文件切片进入的同文件嵌入」这一场景暴露。
- **为何不修**：统一语义需权衡（整文件兜底可能引入大段非预期内容，切片兜底则与枚举文档不符），登记待后续统一或补文档。
- **绕过**：确保引用的 section 存在；或对该类引用改用 `Fail`/`Skip` 策略显式处理。

源码定位：`src/lib.rs`（`embed_same_file`、`MissingSectionStrategy`）。

## 桌面端：ureq 2.12 小响应体 panic 面（跟进观察项）

- **现象**：更新检查/下载遇到「小响应体 + 服务器提前截断断流」的组合时，ureq 内部 panic（进程 exit 101），破坏边车 0/1/2 退出码契约。
- **根因**（源码核实勘误）：panic 点在 `request.call()` 构造 Response 期间的 `stream_to_reader`——小响应体全缓冲路径上 `read_exact`/`return_to_pool` 的 `expect`；**不在** `into_string`（后者无 charset feature 时就是 `into_reader + take + from_utf8_lossy`），换 body 读取方式绕不开。
- **为何不修**：上游 ureq 自认 TODO；触发概率极低（需要服务器在数百字节内断流）。
- **跟进**：升级 ureq 时关注上游修复说明。

源码定位：`src/update.rs`（`check_agent`/`download_agent` 的 ureq 封装）。

## Excalidraw 降级链接会被产物检查报为死链

- **现象**：`--render-diagrams excalidraw` 下，转换失败或处于 `--start-at` 范围外的绘图，其嵌入降级为指向原 vault 路径的普通链接（刻意不导出原文件，保留追溯）；桌面端随后对**导出产物**跑链接检查时，这些链接因目标不存在而进入 broken 报告。
- **设计意图**：降级链接的职责是「可追溯」而非「可点击」——目标本来就不在产物树中；同一警告已在导出事件流（`warning`）中给出。
- **为何不修**：让 check 特判降级形态需要把导出上下文泄漏进无状态的链接检查器，得不偿失；broken 报告如实反映「产物中存在无目标链接」这一事实。
- **绕过**：先修好转换失败的原因（工具安装、绘图文件本身）再导出；或检查 vault 源（GUI 默认）而非产物。

源码定位：`src/lib.rs`（`embed_excalidraw_events` 的 Failed 分支）。
