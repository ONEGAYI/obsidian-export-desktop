# 代码审查派发约定

> 触发：对分支或 PR 派发正式审查子代理时读本文件。日常小修与自检不需要。

## 两轴模式

审查分两轴并行子代理，互不污染上下文（一轴通过不能掩盖另一轴失败）：

- **Standards 轴**：diff 是否符合仓库文档化标准——AGENTS.md 的架构硬约束与「桌面端开发」段约定；叠加 Fowler 坏味道基线（`Duplicated Code`、`Data Clumps`、`Speculative Generality` 等）作为判断项，**仓库文档化标准优先于基线**（仓库明确背书的写法不按基线报）。
- **Spec 轴**：diff 是否忠实实现规格——(a) 缺失/部分实现、(b) 范围蔓延、(c) 看似实现但可疑。规格事实源是远端 issue：`gh issue view <N> -R ONEGAYI/obsidian-export-desktop`（**必须带 `-R`**，本仓库目录下 gh 会解析到 upstream），本地 `.scratch/` 快照仅作参考；**issue 评论里登记的取舍与观察项不要重复报告**。

## brief 必含

- diff 命令用三点形式 `git diff <fixed>...HEAD`，附 commit 清单；派发前先验证锚点可解析、diff 非空
- 各轴的来源：Standards 轴给标准文件路径清单，Spec 轴给 issue 号与快照路径
- 输出格式约定：按严重度分级（blocker / major / minor / 取舍登记）+ 一行总判定

## 证据规则（v26.9.3 实况教训）

- 每条发现必须带可验证证据：`文件:行号` + 引用相关 hunk，只凭提交信息不算
- **UI/样式类结论必须有像素实测或源码行定位**。按 token 命名推断视觉行为曾产出误报：审查者把 `--background` token 当页面底色、断言「页面与面板同色」，实际页面由根容器的 `--background-secondary` 铺色，靠代测像素采样对质才澄清
- 推断无法实证时必须显式标注「推断」，交主代理核对后才能进结论
- 与 diff 上下文明显矛盾的结果（描述对不上号）应回头核对证据链而非直接采信

## 聚合

主代理分轴呈现两份报告（不跨轴重排、不合并重定级），然后逐条判定处置：立即修 / 开 issue 登记 / 注释登记为有意取舍。
